- **反馈人／来源：**稳如泰山，11 月 10 日补采新增。
- **问题实质与源码根因剖析：**
  - 玩家观察到“删除后隐藏但仍占槽”“清空后重新出现”，涉及的可能不是单一文件删除，而是 **Flash SOL、启动器 JSON 副本、删除标记及槽位目录**之间的状态关系。
  - 本轮直接核对了 `launcher/web/modules/archive-editor.js:1274–1294` 的 `onResetSlot()`：
    - 确认框明确写明：仅清理启动器侧 JSON 备份与删除标记，**不影响 Flash 内部 SOL**。
    - 成功后调用 `refreshList()`，并显示笼统的“清理成功”。
  - 因而，“清理删除标记后，尚存的 SOL 被重新发现”是**符合现有入口语义的解释方向**，但尚不能认定玩家使用的就是这个入口，更不能直接认定槽位占用问题已经定位。
- **代码与分支核查：**
  - 工单基线为 [`5e9da9048`](https://github.com/FlashNightModReborn/CrazyFlashNight/commit/5e9da9048)，其发布主题不是存档删除修复。
  - 当前可见提交中没有 [#224](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/224) 的修复记录。
  - `launcher/src/Save/SaveSlotCatalog.cs` 是后续目录与槽位枚举排查入口；本轮未读取其实现，不对其内部行为下结论。
- **当前结论与下一步建议：**
  - **建议提级 P1，先诊断、后修改。**目前没有坏档证据，但误导性的删除／清空操作可能诱发玩家反复删文件或覆盖。
  - 使用隔离数据分别记录：删除前、删除后、清理后、重启后四个时点的 SOL、JSON、删除标记与槽位列表。
  - 可以先微修清理成功提示，但**文案改善不能作为 [#224](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/224) 整单修复关闭的依据**。

### 4.1 🚨 严重性拔高 / 建议跳过排期优先处置（High-Severity Escalations）

#### ① [#224](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/224)：不是单纯“按钮文案问题”，而是存档生命周期与槽位语义问题

**建议：按 P1 阻断风险优先核查；若证实会误覆盖其他存档、丢失唯一有效副本，再升级为数据安全级紧急处置。当前不能直接宣称已经发生数据丢失。**

所附 `launcher/web/modules/archive-editor.js:1274–1294` 已说明一个关键事实：

- `1277` 行的确认文案明确承诺：清理 launcher 侧 JSON 备份和删除标记，**不影响 Flash 内部 SOL**。
- `1293` 行发送的是 `reset` 命令，不是可据名称推断为“删除全部存档”的命令。
- `1285` 行随后刷新列表；`1283` 行却只显示泛化的“清理成功”。

由此必须拆开三个问题：

1. **用户点击的是哪个入口？**删除角色、释放槽位、清理启动器副本，不能共享一个含糊的“清空”解释。
2. **槽位由谁判定占用？**SOL、JSON、删除标记之间，哪些参与枚举，哪个是权威来源？
3. **清理删除标记会产生什么结果？**如果枚举逻辑会重新发现仍存在的 SOL，撤掉删除标记后，旧存档可能重新出现。这是需要验证的机制风险，不是已经由前端片段证明的后端行为。

**建议先补一张操作契约表，而不是先改删除代码：**

| 操作 | SOL | launcher JSON | 删除标记 | 刷新后的槽位预期 |
|---|---|---|---|---|
| 清理启动器副本 | 保留 | 按当前文案应清理 | 按当前文案应清理 | 必须说明是否可能重新发现 SOL |
| 删除／释放槽位 | 需明确产品承诺 | 需明确 | 需明确 | 必须与入口承诺一致 |
| 恢复／重新导入 | 需明确来源 | 需明确生成规则 | 需明确处理规则 | 不得静默覆盖其他有效存档 |

这张表需要由前后端共同核对，不能只改前端后便宣告 [#224](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/224) 关闭。

**优先交付边界：**

- 先让界面准确说明“删了什么、保留什么、是否释放槽位”。
- 再验证刷新、重启及再次进入游戏后的枚举结果。
- 任何扩大删除范围的修复，都要先有备份、失败回报及目标槽位校验；**不能为解决“看起来没清掉”而顺手增加 SOL 删除。**

#### ② 非方形掉落图标避免被强拉成正方形

- **文件：**`launcher/src/Guardian/Hud/Loot/LootIconCatalog.cs`
- **准确位置：**`372–384` 行的 `CreateThumb`，具体替换 `383` 行绘制方式。
- **源码事实：**目前始终将整张源图画到 `ThumbSize × ThumbSize`，非方形输入会改变宽高比。
- **建议改法：**若图标规范没有要求拉伸填满，改为等比缩放、居中透明留边：

```csharp
float scale = Math.Min(
    (float)ThumbSize / full.Width,
    (float)ThumbSize / full.Height);
float width = full.Width * scale;
float height = full.Height * scale;

g.Clear(Color.Transparent);
g.DrawImage(
    full,
    (ThumbSize - width) / 2f,
    (ThumbSize - height) / 2f,
    width,
    height);
```

保留现有高质量插值、像素格式和异常释放逻辑。

**最小回归：**方形、横长、竖长、透明边缘各一张；确认方形资源不退化，长条资源不变形。如果现有资源契约明确要求铺满，则不直接采用此改法。

**边界：**这是 launcher 掉落图标缩略图改进，**不是 [#210](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/210) Lady 动态光效修复**。

LogManager.Log(

**收益：**现有日志只保留 URI 和 `ex.Message`；补齐实际拼接路径及异常上下文，便于区分资源路径、解码器和缩略图生成阶段的问题，减少来回索要环境信息。

**最小回归：**正常图片仍正常；损坏图片仍返回 `null`，但日志信息足够定位。`347` 行“文件不存在”的提前返回不在这个异常分支内，不能声称本改动覆盖了所有缺图原因。

**边界：**不改变缓存策略、不增加重试、不触碰 `363–367` 行的位图所有权处理；这是诊断补强，不计作业务 Bug 已修复。

**本轮不凑数的两类改动：**

- 玩家模板虽然已有精确行号，但换弹门控和状态切换不应被包装成“随手删一个条件”。相关判断放到下节处理。
- 合成地点／材料字典检索片段实际是 **grep 超时**，没有取得有效脚本路径和行号。不能据此宣称脚本不存在，更不能编一个 `tools/...` 路径进入微改清单。

### 4.3 ⚖️ 待设计裁决与架构关注项（Design Rulings & Architectural Watch）

#### A. [#215](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/215) 翻滚换弹与幽灵装填：先决定是否同一种“换弹交易”

需要 fs 明确：

1. 翻滚换弹是否触发幽灵装填，还是只执行技能自身的基础装填；
2. 若触发，是否沿用手动换弹的弹药／资源消耗；
3. 条件不满足时，是退回普通装填、部分补装，还是不触发；
4. 中断、受击或切武器后，已扣资源与已生成弹量如何结算。

**架构建议：**不要仅在翻滚动作末尾复制一遍手动换弹代码。应明确两条入口是否共用同一套装填结算，并保证一次动作最多结算一次。

验收需同时对账**动作、弹匣、备弹、幽灵弹或相关资源**；只看“弹匣满了”不足以通过。

#### B. [#222](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/222) 卡宾套件：先裁决改装后的武器身份

本段没有足够信息确认套件的最终分类规则，因此不预设它一定应算某一枪种。fs 至少需要决定：

- 它只改变外观／射击行为，还是改变武器分类；
- 技能和配件适配按原武器身份还是改装后身份判断；
- 装备槽位、持枪动作、弹药规则分别是否变化；
- 拆卸套件后，哪些属性和状态必须恢复。

**架构关注：**基础物品身份、派生战斗属性、UI 展示分类应分清。不要为让某一处适配通过，直接修改永久物品 ID，继而影响背包、存档、配件及技能判定。

先形成一张“改装前／改装后”的契约表，再决定改动落在哪层；避免多个系统各自硬编码一次“卡宾例外”。

#### C. [#223](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/223) 技能使用等级：学习条件不等于施放条件

[#213](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/213) 的“可学”角标修正，只解决学习资格的展示，不能顺带证明 [#223](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/223) 已解决。

需 fs 裁决：

- 等级是只在学习时检查，还是每次使用也检查；
- 已学习技能遇到降级、读入旧档或其他等级变化时，是否仍可使用；
- 若存在基础等级与加成后等级，使用门槛采用哪一个；
- 不满足条件时，技能保留但禁用，还是采取其他明确规则。

**实现原则：**学习资格、使用资格分别建模，各自让 UI 和实际执行复用一致判断。不要在施放失败时自动删技能，也不要只把按钮置灰，却让快捷键或其他调用入口继续绕过。

#### D. [#212](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/212) 肉鸽保存：保存粒度与恢复语义必须先定

需要明确保存的是哪一层：

- 长期角色进度；
- 当前局的检查点；
- 可跨退出恢复的完整局内状态。

这三者不是同一个功能，不能因为 launcher 已有 JSON 副本，就推导出肉鸽局内恢复已经具备条件。

fs 应拍板：

1. 允许在哪些时点保存：房间结束、安全点，还是任意退出；
2. 正常退出、崩溃和强制关闭，分别恢复到哪里；
3. 死亡后快照如何失效，结算与恢复如何避免重复发奖；
4. 随机进度、已领取奖励和消耗状态是否必须随快照固定；
5. 旧版本快照是否兼容；不兼容时如何安全提示。

**架构建议：**先保证恢复结果有效、结算不重复，再扩展保存频率。快照应带版本与明确的局实例标识；它与长期存档的关联、权威来源和失败处理需要单独定义，不能与 [#224](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/224) 的“清理启动器副本”混成一个操作。

#### E. [#216](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/216)／[#217](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/217)：走、跑、射击与换弹的组合规则需要统一

片段中存在一个明确的实现差异：

- `551–565` 行：横向行走会在满足移动射击条件时保留射击朝向，并设置 `isBackwardsShooting`。
- `580–587` 行：已展示的横向奔跑分支直接改变朝向，没有同样的判断。

这是 **[#217](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/217) 的可疑点，不是已确认根因**。若 fs 确认奔跑中也应保向，可考虑复用行走分支的判定；但仍需检查后续对 `isBackwardsShooting` 的消费及动作支持，不能只凭片段宣布修复。

[#216](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/216) 还需要确认：换弹期间允许的行走／奔跑切换，是否应保持原装填过程。重点检查 `557`、`565`、`571`、`574` 等状态切换与换弹时间线的交互，不能直接删掉状态切换来“保住换弹”。

**设计顺序应是：**先列允许的组合，再统一入口与退出约定；不要让走路、跑步、技能各自拥有一套互相覆盖的换弹规则。

#### 建议推进顺序

1. **先止住阻断风险：**[#224](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/224) 核清操作语义与槽位枚举；[#214](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/214) 建立可复现状态链；[#221](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/221) 确认是否卡必经流程。
2. **并行合入小补丁：**文案、缩略图表现及日志可小提交推进，独立验收，不捆绑状态机重构。
3. **集中请 fs 裁决：**优先解决会阻塞实现的规则问题；[#215](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/215) 与 [#216](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/216)／[#217](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/217) 一起审视，避免修改互相打架。
4. **裁决后再承诺交付：**为 [#222](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/222)、[#223](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/223)、[#212](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/212) 补齐规则表和测试矩阵，再给实现排期。本文顺序是建议，不代表已获维护者确认的日程。

## 今日结论

- **最应前移的是 [#224](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/224)、[#214](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/214)，以及确认阻断流程后的 [#221](https://github.com/FlashNightModReborn/CrazyFlashNight/issues/221)。**它们分别影响存档操作可信度、战斗可控性和任务链可达性，不宜被普通表现项挤到后面。
